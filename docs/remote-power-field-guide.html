Remote Power Field Guide

How to wake a PC that is fully powered off, put it to sleep, and shut it down — all from a browser tab, over your own network. Written for someone who has never touched a BIOS power setting before. Works for any desktop with a wired network card.

How the three pieces fit together

Waking a PC and shutting one down are completely different mechanisms. Understanding which is which saves you hours of debugging the wrong half.

Waking happens in hardware. When you shut a PC down it is not really off — the power supply keeps a low-voltage rail alive, and your network card sips from it. The card sits there watching every packet on the wire. When it sees a specially formed "magic packet" containing its own MAC address, it electrically pokes the motherboard, and the machine boots. No software is involved, because no software is running.

Sleeping and shutting down happen in software. The PC is already on, so something running on it has to receive the request and act. That something is Sleep-On-LAN (SOL), a tiny daemon you install on the PC. It listens on an HTTP port and exposes URLs like /sleep and /halt.

UpSnap is the web dashboard that drives both: it sends the magic packet to wake, and calls SOL's URLs to sleep or shut down.

What you need before starting

A desktop PC with a wired ethernet connection (Wi-Fi wake is a different, far less reliable feature and is not covered here). Administrator access on that PC. UpSnap already installed somewhere on the same network. And physical access to the PC, because Stage 1 happens before Windows loads.

Placeholders used throughout

Replace <PC-IP> with the target PC's address, <PC-MAC> with its MAC, <UPSNAP-IP> with the machine running UpSnap, and <BROADCAST> with the subnet broadcast address (for 192.168.1.0/24 that is 192.168.1.255).

Stage 1

BIOS / UEFI — keep the card powered

If the firmware cuts power to the network card when the PC shuts down, nothing you do in Windows can help. Settle this first.

  1. Enter the firmware setup.

    Restart and press Del or F2 repeatedly as it boots. If it flies past too fast, hold Shift while clicking Restart in Windows, then choose Troubleshoot → Advanced options → UEFI Firmware Settings.

  2. Find the power management section.

    Usually Advanced → APM Configuration on ASUS, Settings → Advanced → Wake Up Event Setup on MSI, Power Management on Gigabyte and ASRock.

  3. Turn wake-from-network on.

    Its name varies by vendor. Set whichever of these you find to Enabled:

    • Power On By PCI-E / PCI — ASUS, ASRock
    • Resume By PCI-E Device — Gigabyte
    • Resume By PME or PME Event Wake Up — MSI, older boards
    • Wake on LAN or Wake on Onboard LAN — Dell, HP, Lenovo prebuilts

  4. Turn off the power-saving settings that starve the card.

    • ErP Ready (also EuP) → Disabled
    • Deep Sleep / Deep S5 → Disabled

    These exist to meet European standby-power limits by cutting the +5 V standby rail when the PC is off. That rail is exactly what your network card runs on.

  5. Save and exit.

    Usually F10. The PC reboots into Windows.

The single most common blocker

ErP Ready left enabled is the number one reason wake-from-shutdown fails while wake-from-sleep works perfectly. Sleep keeps the rail alive regardless; only a full shutdown exposes the setting. If you take one thing from this stage, take this.

Every BIOS update undoes this stage

Flashing new firmware resets CMOS to factory defaults, which quietly puts ErP Ready back to Enabled and Power On By PCI-E back to Disabled. The Windows half of the setup is untouched and keeps reporting healthy, so the machine looks fine right until the next shutdown — at which point it is unreachable with no way to wake it remotely. Re-apply this stage after any BIOS update, before you power the machine down and walk away from it.

Checkpoint

Shut the PC down completely, then look at the ethernet port on the back. The link light should still be lit or blinking. If it is dark, the card has no standby power and you have missed a setting above. Do not continue until that light is on.

Stage 2

Windows and the network card

Three separate settings, in three separate places, all of which must be right. Windows does not present them together, which is why this trips people up.

  1. Turn off Fast Startup.

    Windows' "Shut down" is a lie by default — it hibernates the kernel instead of shutting down, and the network card gets torn down in the process. Open Control Panel → Power Options → Choose what the power buttons do, click Change settings that are currently unavailable, then untick Turn on fast startup and save.

    Or from an Administrator PowerShell:

    powercfg /hibernate off

    That disables Fast Startup and hibernation together. To keep hibernation but drop Fast Startup, use the Control Panel checkbox instead.

  2. Allow the card to wake the PC.

    Press Win+X → Device Manager → expand Network adapters → double-click your wired card → Power Management tab. Tick all three:

    • Allow the computer to turn off this device to save power
    • Allow this device to wake the computer
    • Only allow a magic packet to wake the computer

    That third one matters more than it looks. Without it, ordinary broadcast traffic will wake the PC at random hours and you will never work out why.

  3. Set the driver properties — including the one for shutdown.

    Same dialog, Advanced tab. The list differs by manufacturer. Set what applies:

    PropertySet toFound onWhat it covers
    Wake on Magic Packet Enabled Intel, Realtek, Broadcom Wake from sleep and hibernate (S3 / S4)
    Enable PME Enabled Intel Wake from full shutdown (S5)
    Shutdown Wake-On-Lan Enabled Realtek Wake from full shutdown (S5)
    Wake on Pattern Match Disabled Intel, Realtek Stops random traffic waking the PC
    Energy Efficient Ethernet Disabled Most vendors Can drop the link before a packet lands
    Green Ethernet Disabled Realtek Same problem, different name

  4. Verify from PowerShell rather than trusting the checkboxes.

    Get-NetAdapter | Where-Object Status -eq 'Up'

Get-NetAdapterAdvancedProperty -Name 'Ethernet' |
    Format-Table DisplayName, DisplayValue -AutoSize

powercfg /devicequery wake_armed

    Substitute your adapter's name for Ethernet if it differs. Your network card must appear in the wake_armed list. If it does not, step 2 did not take.

The separate-settings trap

"Wake on Magic Packet" and the S5 property (Enable PME on Intel, Shutdown Wake-On-Lan on Realtek) are two different settings covering two different power states. Enabling only the first gives you a PC that wakes reliably from sleep and ignores you completely after a shutdown — the exact symptom most guides never explain.

This will break again later

Network driver updates reset every property on the Advanced tab to its factory default, and the S5 property ships disabled. If Wake-on-LAN mysteriously stops working months from now, come back to step 3 before suspecting anything else.

Stage 3

Prove the wake works

Test this on its own, before adding SOL or UpSnap. Chasing a wake failure through three layers at once is miserable; chasing it through one is easy.

  1. Write down the PC's MAC address.

    Get-NetAdapter | Format-Table Name, MacAddress, Status

    You want the MAC of the wired card that is Up. Ignore anything belonging to VMware, VirtualBox, Hyper-V, Tailscale or a VPN — those adapters do not exist when the PC is off, and pointing your tools at one guarantees failure.

  2. Shut the PC down. Not sleep — a real shutdown.

  3. Send a magic packet from another machine on the same network.

    From Linux or a container:

    wakeonlan <PC-MAC>
# or
etherwake -i eth0 <PC-MAC>

    From another Windows PC, in PowerShell:

    $mac  = '<PC-MAC>' -replace '[:-]',''
$pkt  = ([byte[]](,0xFF * 6)) + ((1..16) | ForEach-Object {
            [byte[]] ($mac -split '(..)' -ne '' | ForEach-Object { [convert]::ToByte($_,16) })
        })
$udp  = New-Object System.Net.Sockets.UdpClient
$udp.Connect(([System.Net.IPAddress]::Broadcast), 9)
$udp.Send($pkt, $pkt.Length)
$udp.Close()

  4. The PC should power on within a couple of seconds.

    If it does, the hard part is done — everything after this is software you can debug with a running machine in front of you. If it does not, go to Troubleshooting before continuing.

Why the sender must be on the same subnet

A magic packet is normally sent as a broadcast, and routers do not forward broadcasts between subnets. If UpSnap lives on a different VLAN from the PC, the packet dies at the router. Two fixes: run UpSnap on the same subnet as the PCs it manages (simplest by far), or add a static ARP entry on the router mapping the PC's IP to its MAC so a unicast packet can be delivered to a machine that is switched off.

Checkpoint

The PC boots from a full shutdown when you send a magic packet. Leave it running — Stage 4 happens on this machine.

Stage 4

Install Sleep-On-LAN on the PC

This gives you sleep and shutdown. It is one small program plus one config file, running in the background as a system task.

You could instead let UpSnap shut Windows down with net rpc shutdown, but that means storing a Windows username and password in plain text in UpSnap's database, and loosening Windows' remote-access defaults. SOL avoids both: no credentials anywhere, and one daemon that handles sleep and shutdown alike.

  1. Download and unpack it.

    Get the latest release from github.com/SR-G/sleep-on-lan. Create C:\Tools\sleep-on-lan\ and put the Windows 64-bit executable there, renamed to sol.exe.

  2. Create the config file.

    Save this as sol.json in the same folder. Note the doubled backslashes — that is required by JSON, and a single backslash will stop SOL from starting. 

    {
  "Listeners": [
    "UDP:9",
    "HTTP:8009"
  ],
  "LogLevel": "INFO",
  "BroadcastIP": "<BROADCAST>",
  "ExitIfAnyPortIsAlreadyUsed": false,
  "Commands": [
    {
      "Operation": "sleep",
      "Command": "C:\\Windows\\System32\\rundll32.exe powrprof.dll,SetSuspendState 0,1,0",
      "Type": "external",
      "Default": true
    },
    {
      "Operation": "halt",
      "Command": "C:\\Windows\\System32\\shutdown.exe -s -t 0 -f",
      "Type": "external",
      "Default": false
    }
  ]
}

    Each entry in Commands becomes a URL. "Operation": "halt" creates http://<PC-IP>:8009/halt. Add your own if you want, for example a reboot operation running shutdown.exe -r -t 0.

  3. Decide how forceful the shutdown should be.

    CommandBehaviour
    shutdown.exe -s -t 0 -f Immediate. Force-closes everything, no prompts, no way to cancel. Unsaved work is lost.
    shutdown.exe -s -t 30 -f 30-second countdown with an on-screen warning. Cancel from any console with shutdown /a. Safer if you actually sit at this PC.

  4. Open the firewall for SOL — scoped to UpSnap only.

    In an Administrator PowerShell:

    New-NetFirewallRule -DisplayName 'Sleep-On-LAN HTTP' -Direction Inbound `
    -Protocol TCP -LocalPort 8009 -RemoteAddress <UPSNAP-IP> -Action Allow

New-NetFirewallRule -DisplayName 'Sleep-On-LAN UDP' -Direction Inbound `
    -Protocol UDP -LocalPort 9 -RemoteAddress <UPSNAP-IP> -Action Allow

    SOL has no authentication by default. Anyone who can reach port 8009 can shut this PC down with a single web request, so restricting the source address is not optional hardening — it is the only thing protecting the endpoint.

  5. Make it start with Windows.

    sol.exe is a normal console program, so it cannot be registered as a Windows service directly — sc.exe create produces error 1053 when it fails to respond to the service manager. A scheduled task running as SYSTEM does the same job with nothing extra installed. In an Administrator PowerShell: 

    $dir = 'C:\Tools\sleep-on-lan'

$action    = New-ScheduledTaskAction -Execute "$dir\sol.exe" -WorkingDirectory $dir
$trigger   = New-ScheduledTaskTrigger -AtStartup
$principal = New-ScheduledTaskPrincipal -UserId 'S-1-5-18' `
                -LogonType ServiceAccount -RunLevel Highest
$settings  = New-ScheduledTaskSettingsSet -AllowStartIfOnBatteries `
                -DontStopIfGoingOnBatteries -StartWhenAvailable `
                -RestartCount 3 -RestartInterval (New-TimeSpan -Minutes 1)
$settings.ExecutionTimeLimit = 'PT0S'

Register-ScheduledTask -TaskName 'SleepOnLAN' -Action $action -Trigger $trigger `
    -Principal $principal -Settings $settings -Force

Start-ScheduledTask -TaskName 'SleepOnLAN'

    Running as SYSTEM matters: the task starts at boot with nobody logged in, and it has the rights to call the shutdown and suspend APIs.

  6. Check it answers.

    curl http://127.0.0.1:8009/

    You should get XML listing the PC's network interfaces, the active listeners, and your two commands. Open it in a browser on the PC if you prefer.

If nothing is listening

Antivirus is the usual culprit. sol.exe is an unsigned program that opens a network listener and calls shutdown APIs, which looks exactly like malware to a scanner. Check your quarantine and add C:\Tools\sleep-on-lan as an exclusion before debugging anything else.

Sleep may actually hibernate

If hibernation is enabled, Windows' SetSuspendState call hibernates (S4) rather than sleeping (S3), whatever arguments you pass it. That is usually fine — Wake-on-LAN works from both. If you specifically want real sleep, run powercfg /hibernate off first. And note that verifying the task afterwards from a non-administrator prompt reports Access is denied or not found, because a SYSTEM task is hidden from ordinary users — that does not mean it failed. Check from an elevated prompt.

Checkpoint

Reboot the PC and run the curl above again without starting anything by hand. If SOL answers, it is surviving reboots correctly.

Stage 5

Wire it up in UpSnap

Everything now works; this stage just points the dashboard at it.

  1. Add the device, or edit it if UpSnap discovered it already.

    FieldValue
    NameAnything you like
    IP<PC-IP>
    MAC<PC-MAC> — the wired card, not a virtual adapter
    NetmaskUsually 255.255.255.0

    If the PC runs VMware, VirtualBox or Hyper-V, check this carefully. Auto-discovery sometimes picks a virtual adapter, and both waking and shutting down will silently target a network card that does not exist when the machine is off.

  2. Make sure the PC answers ping.

    UpSnap decides whether a device is online by pinging it, and it hides the sleep and shutdown buttons on any device it believes is off. A PC that is running perfectly but blocks ICMP therefore shows as powered down with no controls — which looks exactly like a broken Wake-on-LAN setup, and sends people back to re-checking BIOS settings that were never the problem.

    Windows blocks inbound ping by default. In an Administrator PowerShell: 

    Get-NetFirewallRule -Direction Inbound |
    Where-Object { $_.DisplayName -like 'File and Printer Sharing (Echo Request*' -and
                   $_.Profile -notmatch '^Public$' } |
    Enable-NetFirewallRule

    Verify it from another machine, never from the PC itself — local traffic bypasses the firewall entirely, so a PC can always ping its own address and will report success even while every other host on the network gets nothing.

  3. Fill in the Sleep-On-LAN section.

    FieldValue
    Enable Sleep-On-LANOn
    SOL Port8009 — must match the HTTP: listener in sol.json

  4. Fill in the Shutdown section.

    FieldValue
    Shutdown command curl -s -m 5 http://{{ DEVICE_IP }}:8009/halt
    Shutdown Timeout 30
    Enable shutdown cron Off, unless you want it powering down on a schedule
    Require Confirmation On — strongly recommended with an immediate shutdown command

    {{ DEVICE_IP }} is an UpSnap placeholder; it substitutes the device's real address when the command runs. {{ DEVICE_MAC }} works the same way.

  5. Understand what Shutdown Timeout actually does.

    It does not delay the shutdown. It is how long UpSnap waits before re-checking whether the device went offline. The delay before the PC powers off is set entirely by the -t value in sol.json. Set the UpSnap timeout comfortably higher than that -t value, or UpSnap will re-probe while the countdown is still running and report the device as still online.

  6. Test the path before pressing anything destructive.

    The shutdown command runs where UpSnap runs, so test it from there. If UpSnap is in Docker: 

    docker exec upsnap curl -s -m 5 http://<PC-IP>:8009/

    If UpSnap runs as a plain binary, on its host or in an LXC:

    curl -s -m 5 http://<PC-IP>:8009/

    The trailing / is deliberate — that is the harmless status page. Do not test with /halt unless you mean it.

  7. Save, then try all three buttons: wake, sleep, shutdown.

If UpSnap is not the Docker image

The official Docker image ships with curl, sshpass and Samba preinstalled. A bare LXC or a manual binary install has none of them. UpSnap will hand your command to the shell, get curl: not found, and report a failed shutdown with no useful explanation. Run command -v curl on that host first, and apt install -y curl if it is missing.

Troubleshooting

Find your symptom; the cause is almost always in the same row.

SymptomMost likely causeFix
UpSnap shows the PC as off while it is clearly running, and the sleep / shutdown buttons are missing The PC blocks inbound ping, so UpSnap's online check fails; it hides controls on devices it thinks are off Enable the inbound ICMPv4 echo rules (Stage 5 step 2). Test the ping from another host, not from the PC itself
Everything broke right after a BIOS update Flashing firmware reset CMOS, re-enabling ErP Ready and disabling Power On By PCI-E Re-apply Stage 1. The Windows settings survived, so only the firmware half needs redoing
Wakes from sleep, but not after shutdown The S5-specific driver property is off, or ErP Ready is on in BIOS Set Enable PME (Intel) or Shutdown Wake-On-Lan (Realtek); disable ErP Ready
Nothing wakes it at all, link light dark when off No standby power reaching the card BIOS: disable ErP / Deep Sleep, enable Power On By PCI-E
Worked for months, suddenly stopped A driver update reset the Advanced tab to defaults Re-apply Stage 2 step 3
Works from a PC on the same switch, not from UpSnap UpSnap is on a different VLAN; broadcasts do not cross routers Move UpSnap to the same subnet, or add a static ARP entry on the router
Wakes by itself at random times Wake on Pattern Match enabled, or a wake timer Tick Only allow a magic packet; run powercfg /lastwake to identify the source
Shutdown button does nothing curl missing where UpSnap runs, or the firewall blocks 8009 Run the Stage 5 step 5 test and read the actual error
SOL not listening after a reboot Antivirus quarantined sol.exe, or the task did not register Check quarantine, add an exclusion, re-run the registration from an elevated prompt
Sleep button hibernates instead Hibernation is enabled, so SetSuspendState hibernates Accept it, or run powercfg /hibernate off
Wake works, but only sometimes Energy Efficient Ethernet dropping the link Disable EEE / Green Ethernet on the Advanced tab

Useful commands to run on the PC

# which devices are allowed to wake this PC
powercfg /devicequery wake_armed

# what woke it last time
powercfg /lastwake

# which sleep states the hardware supports
powercfg /a

# is Fast Startup off? 0 means yes
Get-ItemProperty 'HKLM:\SYSTEM\CurrentControlSet\Control\Session Manager\Power' `
    -Name HiberbootEnabled

Appendix

Linux targets

The same three stages apply. Only Stage 2 and Stage 4 differ.

Enable Wake-on-LAN

Check what the card supports and whether it is armed:

sudo ethtool eth0 | grep -i wake
# Supports Wake-on: pumbg
# Wake-on: d          <- d means disabled

Turn it on. g means "wake on magic packet":

sudo ethtool -s eth0 wol g

That resets at reboot. To make it stick with NetworkManager: 

nmcli connection modify "Wired connection 1" 802-3-ethernet.wake-on-lan magic

Or with a systemd unit, if you are not using NetworkManager:

sudo tee /etc/systemd/system/wol.service <<'EOF'
[Unit]
Description=Enable Wake-on-LAN
After=network-online.target

[Service]
Type=oneshot
ExecStart=/sbin/ethtool -s eth0 wol g

[Install]
WantedBy=multi-user.target
EOF

sudo systemctl enable --now wol.service

Sleep-On-LAN commands

Same sol.json structure, different commands:

"Commands": [
  {
    "Operation": "sleep",
    "Command": "systemctl suspend",
    "Type": "external",
    "Default": true
  },
  {
    "Operation": "halt",
    "Command": "systemctl poweroff",
    "Type": "external",
    "Default": false
  }
]

Run it as a systemd service so it starts at boot as root:

sudo tee /etc/systemd/system/sleep-on-lan.service <<'EOF'
[Unit]
Description=Sleep-On-LAN
After=network-online.target

[Service]
ExecStart=/opt/sleep-on-lan/sol
WorkingDirectory=/opt/sleep-on-lan
Restart=always

[Install]
WantedBy=multi-user.target
EOF

sudo systemctl enable --now sleep-on-lan.service

Sleeping over UDP instead of HTTP

SOL can also be triggered by a magic packet on UDP 9, using the machine's MAC address reversed — so a card with c4:d9:87:7a:78:35 sleeps when it receives a packet for 35:78:7a:87:d9:c4. The reversal is what stops an ordinary wake packet from immediately putting a running machine back to sleep. UpSnap uses the HTTP path instead, because it is easier to authorise and gives a real success or failure response.

Order matters throughout: firmware, then Windows, then a bare wake test, then SOL, then UpSnap. Each stage is testable on its own, and skipping ahead means debugging several layers at once.
